# 经典版前端迁移与新版独立演进

- Status: in-progress
- 确认日期：2026-10-23
- 决策负责人：项目所有者；实现负责人：当前前端维护者。
- 生命周期说明：目标已确认，迁移尚未实施；当前先搁置经典版，开展新站前端优化。此状态不表示已实现双界面或已开始迁移。

## 背景

当前新站采用了不同于旧站的信息架构。继续在新版中逐项模仿旧版，会把新设计与经典体验混为同一验收目标。用户明确确认：staging 未拉取最新数据，数据差异正常；首页差异属于设计变化，不作为本轮界面缺陷或数据修复任务。

此前[前端差距审计](../../../docs/audits/frontend-gap-2026-10-23.md)保留观察证据，但其中以差异直接推定修复优先级的建议已被本决策部分取代。移动溢出等独立可用性问题不因设计变化而自动关闭。

## 决策

### 两套界面，共用同一系统

- 长期目标是让用户选择经典版或新版界面，不建设两套独立产品系统。
- 两版共用账号、内容、认证、权限、安装状态、现有后端协议及 SillyTavern 客户端桥接，不复制数据或后端。
- 经典版以只读 `../workshop-legacy` 的 `15303df5e3b30aa7f3fc924296ae57497a7ad09a` 源码为迁移基准。用户认为源码与旧站线上应一致；若发现差异，先按源码处理并记录，不把线上等价当成已验证事实。
- 经典版迁到已经选择的 React、Vite、Tailwind CSS、shadcn/ui 技术栈。合理复用旧代码；最终形态采用 React 组件，不把整套旧脚本长期塞入 React 容器形成另一套状态系统。确有必要的临时隔离复用必须明确边界和替换条件。
- 两版布局、导航和交互可以独立；先迁移完整用户旅程，再按实际重复提取共享逻辑，不提前以大量经典版条件分支合并两套视图。
- 新版保留自己的设计，不再承担旧站复刻验收。

### 前端迁移不反向驱动旧版 API 恢复

- 现有 API 能支持的功能真实接入，由迁移后的前端适配现行契约。
- 本阶段不为经典版恢复旧接口、增加接口、改 schema 或改后端业务语义。
- 只有新版也独立需要某项能力时，才另行讨论该后端需求；不能以经典版需要为由自动修改后端。
- 旧功能缺少现有后端支持时，先暂缓真实接入；允许迁移界面和本地交互，用隔离 dummy 支撑展示，不要求先打通全部旧功能。
- dummy 必须与真实数据和写入路径隔离，明确区分未接入状态，不伪造保存、发布、安装或审核成功，也不将虚构状态混入真实账号或项目。
- 不因缺少后端接入而默默删除对应界面，也不以 dummy 宣称该功能已完成。

### 功能确认交付物

经典版迁移阶段最终须产出一份供用户逐项确认的功能清单，每项至少列出：旧功能与源码位置、前端迁移情况、现有 API 支持情况、真实接入或 dummy 边界、未接入部分，以及用户决定补上或不做的确认栏。

原先删除或暂缓的旧功能也先按暂缓接入处理，不在迁移时擅自认定永久恢复或永久删除。用户逐项决定后，才能调整最终范围。当前仅记录该交付要求，不提前编造完成情况或替用户选择。

### 当前工作顺序

1. 记录本决策，修正审计对数据和首页差异的判定。
2. 暂时不处理经典版迁移、两版切换或旧功能接入问题。
3. 转向新站前端优化；以新站自身的布局、交互和可用性为对象，不追随旧版布局，不借机扩展后端。

## 考虑过的替代方案

- 继续在新版逐项还原旧站：拒绝，因为会持续混淆新设计与经典版的目标。
- 两套完整前后端：拒绝，因为账号、内容及状态需要保持同一来源，没有拆成两套系统的产品需求。
- 为迁移完整补回旧 API：拒绝，因为本阶段明确只迁前端，缺口应交用户逐项确认。
- 整套旧脚本永久包进 React：不作为最终方案，因为会形成重复的状态与事件管理，不利于后续新版演进。

## 后果与风险

- 经典版在确认接入之前可能有仅展示或本地交互的功能，必须可辨识，不能误导用户。
- 共用系统不代表两版阶段性功能完全一致；所有未接入项需要进入确认清单，不能在视觉迁移中丢失。
- 当前没有决定界面选择的入口、默认版本或偏好持久化机制；这些属于未来迁移设计，不在此次新站优化中擅自实现。

## 验证要求

- 未来经典版迁移逐项核对源码对应的页面与用户旅程，不以构建成功替代行为验收。
- 真实接入项验证现有 API、账号、内容及安装状态的一致性；dummy 项验证不发真实写请求、不伪造成功、与真实状态隔离。
- 经典版专属需求不得引起后端或契约变更；新版共同需求需要单独明确依据和授权范围。
- 新站界面优化验证实际桌面和移动表面、交互及溢出；不得声称因此完成旧版迁移。浏览器操作仍按本机约束仅由 subagent 执行。
