## 12. 术语：checker / attestation / DO

这三者经常被混为一谈，实际是三层不同的东西。

### Checker（检查器）

- 是 EJS / 正则的静态分析器，源码在 `cloudflare/src/utils/ejs-checker/`（`index.mjs`、`syntax.mjs`、`audit.mjs`、`policy.mjs` 等）。
- 通过 esbuild 打成两个浏览器 bundle：
  - `upload-worker.mjs` → `/assets/upload-checker.js`，创作者设备在**上传前**运行；
  - `review-worker.mjs` → `/assets/review-checker.js`，审核者设备在**审核时**对确切待审内容运行，产出 gate、audit snapshot、certification。
- 检查内容：EJS 语法、API 白名单、外链策略、媒体、处理预算、policy 版本等。
- 现状：两个 bundle 以 base64 文本提交在 `src/generated/*.txt`（约 932KB），由 Worker 在启动时解码后当静态文件返回；所以它们被算进 Worker 体积。
- 按 D-05 改为 Static Assets 后，它们应成为普通静态文件（内容哈希命名），不再 base64 进 Worker。

### Attestation（上传收据）

> 现状说明；新实现删除（D-34）。

- 由 `ProjectUploadPreflight` 在服务端签发：内容 hash + userId + kind + checkerRevision，用 `JWT_SECRET` 签名。
- 上传时 `validateAttestedUpload` 只验证收据与**实际字节 hash** 是否一致。
- 代码注释明确：它**不证明**浏览器真的跑过 checker，只证明“这批字节被这个用户用这个 checker revision 预检过”。
- 它的价值是绑定内容而不是替代审核；成本是同一份文件被传两次（预检一次、上传一次）。

### DO（`CodeCheckService`）

- Cloudflare Free：普通 Worker 每请求 **10ms CPU**，Durable Object **30s**。
- `index.ts` 的 `contentServiceKey()` 把 preflight、审核详情/提交、上传、详情 GET 按路径送进 `getByName('project:<id>')`。
- DO 内部直接调用同一个 Hono app（`app.fetch(request, this.env)`）；认证、权限、revision、R2 规则都在，DO 不是旁路。
- 作用有两个：把大 JSON 解析/摘要计算移出 10ms 预算；同一 project id 天然串行，减少并发写交错。
- 不存业务数据。DO 本身是合理的平台用法，**问题只在“用正则再写一遍路由表”**。

### 当前信任链

```text
创作者浏览器 checker（advisory，只记录 gate）
→ 上传：服务端校验结构/大小/hash（单次）
→ DO 运行 review-checker（权威）
→ pass/warn 自动发布；block/超时转人工
```

## 13. 审核流程（新模型）

### 分层

| 层 | 运行位置 | 作用 | 是否被信任 |
| --- | --- | --- | --- |
| 上传前检查 | 创作者浏览器 | 即时提示；作者可在不通过时确认后继续上传 | **记录但不信任**。只作为路由信号与审计 |
| 自动检查 | Durable Object（30s CPU） | 对提交内容跑完整 checker | **权威**，记录版本、hash、耗时、结果 |
| 人工复核 | 管理页（DO 报告） | 基于 DO 报告一票通过/拒绝；本地重跑仅辅助 | **信任审核者**，结果绑定内容与 revision（D-31） |
| 人工补充 | 管理页 | 处理 block、超时、申诉、抽查 | 覆盖自动结果，写审计 |

### 客户端检查的记录

上传时写入以下字段（仅路由与审计，不构成授权）：

- `client_gate`: `pass | warn | block`
- `client_checker_revision`: engine + policy version
- `client_warning_count`
- `client_acknowledged`: 作者在不通过时是否确认继续上传
- `client_checked_at`

恶意客户端伪造 `pass` 不会绕过安全检查，因为自动检查仍会独立执行并决定是否 block；伪造 `block` 只会让自己进入人工队列。

### 路由

| 客户端 | 自动检查 | 结果 |
| --- | --- | --- |
| pass / warn | pass | 自动发布 |
| pass / warn | warn | 自动发布 + 警告标记 |
| pass / warn | block | 人工队列（附自动检查报告） |
| block | **不运行** | 人工队列（附客户端报告摘要，标记为未验证） |
| 缺少标记 | **不运行** | 人工队列 |
| pass / warn | 超时 | 重试；达上限转人工 |

- **客户端 block 不消耗 DO**：已知需要人工的内容不再跑自动检查。
- **没有自动拒绝**：自动检查只决定“发布 / 转人工”。拒绝由人工完成。
- `warn` 视为通过，但前台必须在项目卡片与详情显示“有警告”，并能展开规则条目。
- **审查策略唯一来源是 checker 的 gate**：`pass / warn / block` 由规则定义，业务层不做项目类型、文件大小之类的额外人工判断；需要人看的规则直接在 checker 里输出 `block`。
- 缺少客户端标记（例如直接调用 API）视为需要人工，同样不跑 DO。

### 状态机

```text
draft
  → submitted
  → checking（租约）
      → auto_published（pass / warn）
      → needs_human（block 或超时达上限）
  → published
  → rejected（仅人工）
```

### 调度

- 调度器是 Worker 的 `scheduled`（Cron Trigger），不是 DO 定时任务。
- cron 从 D1 领取 `submitted`，按项目调用 `getByName('project:<id>')`；DO 提供 30s CPU 与按项目串行。
- 领取使用条件更新 + 租约，过期回收；每次 cron 限制并发。
- Free 的 DO 额度约 3,300 次 30 秒检查/天，足够。

### 自动发布

- pass / warn 直接发布，无需人工查看。
- 报告完整入库（引擎/策略版本、content hash、耗时、findings 摘要），供事后审计与 checker 规则回看。
- 强制人工的规则统一输出 `block`，不要在业务层写“这个类型要人工”的散落判断。
- 发布后仍保留管理员下架/撤回路径。

### 人工

- 审核者基于 DO 报告一票生效：通过即发布，失败即拒绝；本地重跑必须同 revision，只作辅助（D-31）。
- 审核者结果必须绑定 `submission_id + content_hash + checker_revision`。
- 自动结果与人工结果都写审计；人工覆盖自动结果需填写理由。
